# DESIGN-004: The `.cromwell/` Configuration Compartment

**Status:** Approved — 2026-07-20 ([REVIEW-001](../reviews/REVIEW-001-phase-1-package.md)). *Dated notes, 2026-09-28:* §7 records the `max_words` and `one_line` rule kinds and the amendment check, from [SPEC-018](../specs/SPEC-018-decisions.md); and the `contains_text` rule kind and the fenced-code rule, from [SPEC-019](../specs/SPEC-019-bugs.md).
**Date:** 2026-07-20
**Parent:** [vision-v1](../vision/vision-v1.md) §7 (config compartment), §12 (Bootstrapping)
**Depends on:** DEC-002 (connection config), DESIGN-002 (dispatch pipeline, tool host), DESIGN-003 (validation, reviewer binding)

## 1. Purpose

Defines the file formats of the third source of truth: `.cromwell/`, the
user-edited configuration compartment (vision §7, §12). Four formats — project
config, roles, skills, and document templates with validation manifests — plus
the pack lock that makes `cromwell upgrade`'s three-way classification
possible. These files are the interface humans use to tune the system; their
schemas are contracts with the same standing as the Postgres schema
(DESIGN-001).

Out of scope: the semantic *content* of the starter-pack files (the reviewer
skill's actual procedure, the spec template's prose). That content is a
quality-critical phase-1 deliverable (SPEC-001 FR-1.1), reviewed like code —
but it is not a format question.

## 2. Principles

1. **User-owned after init.** Cromwell writes to `.cromwell/` in exactly two
   commands: `init` (copy the starter pack) and `upgrade` (per-file, with
   explicit consent — vision §12). Never as a side effect of anything else.
   The one exception is `pack.lock.yaml`, machine-managed by those same two
   commands.
2. **No state, no secrets.** Config files hold configuration only — entity
   state lives in Postgres, documents live in the repo (vision §12). Secrets
   appear as environment-variable *names*; values live in the environment
   (SPEC-001 NFR-4).
3. **Strict parsing.** Unknown keys are errors. A typo fails loudly at load,
   never silently configures nothing.
4. **Read fresh, fail fast.** Roles, skills, and manifests are re-read per
   dispatch (DESIGN-002 O-6). `cromwell serve` refuses to boot on any invalid
   file (§9).
5. **Plain formats.** YAML for structure, Markdown with YAML front matter for
   prose. No templating language: the `{{...}}` placeholders in `template.md`
   are inert scaffold text, meaningful only to validation check 4
   (DESIGN-003 §3).

## 3. Directory layout

```
.cromwell/
  config.yaml            # project configuration (§4); generated by init, user-owned
  pack.lock.yaml         # starter-pack provenance (§8); machine-managed
  .gitignore             # ships with one entry: run/
  run/                   # runtime files (unix socket, pid); never committed
  roles/
    spec-reviewer.yaml   # one file per role; the filename is the role name (§5)
  skills/
    review-spec/
      SKILL.md           # front matter + procedure (§6)
  templates/
    spec/
      template.md        # scaffold for new documents of this type (§7)
      manifest.yaml      # validation rules + workflow bindings (§7)
```

## 4. `config.yaml`

Generated by `init`, user-owned from birth (never pack-tracked — §8).
Annotated example, which is also the shape `init` generates:

```yaml
version: 1                     # config format version; migrated only via upgrade (§8)

database:
  url_env: CROMWELL_DATABASE_URL   # name of the env var holding the Postgres URL (DEC-002)

server:
  socket: .cromwell/run/cromwell.sock
  http: null                   # optional TCP listen addr, e.g. "127.0.0.1:7473"
  heartbeat_seconds: 30

budget:                        # governor check 1 (DESIGN-002 §6)
  period: monthly              # monthly | weekly | total (lifetime)
  cap_usd: 100.00
  warn_fraction: 0.8           # audit warning at this fraction of cap
  per_dispatch_cap_usd: 2.00   # projected-cost ceiling per dispatch

providers:
  anthropic:
    api_key_env: ANTHROPIC_API_KEY
    rate:                      # token bucket, governor check 2
      requests_per_minute: 50

models:                        # registry; roles and routing reference these keys
  claude-sonnet-5:
    provider: anthropic        # must be a providers key
    price_per_mtok:            # USD per million tokens (values illustrative)
      input: 3.00
      output: 15.00
      cache_read: 0.30
      cache_write: 3.75

routing: {}                    # per-purpose model override (DESIGN-002 §4 step 4),
                               # e.g. review-spec: claude-haiku-4-5

assignments: {}                # purpose → role for non-document purposes (§5; phase 2)

dispatch:
  workers: 4                   # global worker cap, governor check 4
  max_attempts: 3              # 1 initial + 2 retries (DESIGN-002 §8)
  turn_cap: 30                 # default per-dispatch turn budget
  stall_seconds: 120           # heartbeat_at age before failed-stalled

commands: {}                   # tool-host argv whitelist (DESIGN-002 §5; phase 2), e.g.
                               # run_tests: {argv: ["go", "test", "./..."], timeout_seconds: 600}
```

Field notes:

- **Prices are USD per million tokens** — the convention providers publish in,
  so the table can be checked against a price page by eye. At dispatch claim,
  the referenced model's `price_per_mtok` block is copied into
  `dispatches.price_snapshot` (DESIGN-002 O-4); editing the table never
  rewrites history.
- **`routing`** overrides the *model* only. The role (and therefore identity,
  skill, tools) is unchanged — this is the "cheaper model for first-pass
  reviews" lever from vision §5, nothing more.
- **`budget.period: total`** means a lifetime cap; `monthly`/`weekly` reset on
  calendar boundaries (UTC).

## 5. Roles — `roles/<name>.yaml`

The filename is the role name; there is no `name:` field to drift out of sync.
Example — the shipped starter role, abridged:

```yaml
model: claude-sonnet-5         # key into config.yaml models (required)
skill: review-spec             # skill directory name (optional; injected at
                               # prompt position 2, DESIGN-002 §4 step 3)
identity: |                    # the role's identity block, prompt position 1 (required)
  You are the specification reviewer for this project. You judge whether a
  spec is clear, complete, and testable — you do not rewrite it. ...
tools: []                      # tool-host tool names (DESIGN-002 §5); the outcome
                               # tool is NOT listed here (F-5)
tool_hints: ""                 # optional usage nudges appended to tool definitions
limits:                        # optional overrides of config.yaml dispatch defaults
  turn_cap: 15
```

**Role resolution** (how a dispatch purpose finds its role) has one rule per
purpose class, no search order:

- Document-review purposes (`review-<type>`) resolve from the document type's
  template manifest (§7) — the type owns its reviewer.
- All other purposes (phase 2: `implement-task`, `verify-feature`,
  `estimate`) resolve from `config.yaml` `assignments:`. In phase 1 this map
  is empty.

**Outcome tools are not configurable.** Each dispatch purpose defines its
outcome tool in code (DESIGN-002 §4, O-2); role files cannot add, remove, or
rename it. `tools:` lists only ordinary tool-host tools, enforced as a profile
per DESIGN-002 §5. Phase-1 roles have `tools: []` — the reviewer needs nothing
beyond its outcome tool.

## 6. Skills — `skills/<name>/SKILL.md`

The directory name is the skill name. One file matters:

```markdown
---
description: Procedure for reviewing a specification document
---

# Reviewing a specification

1. Read the validation report before the document ...
```

- Front matter: `description` (required — shown by `upgrade` and future
  listings). No other keys in phase 1; unknown keys are errors (principle 3).
- The body is injected verbatim at prompt position 2 (DESIGN-002 §4 step 3).
- Other files in the skill directory are permitted as reference material for
  humans and are ignored by the loader. Includes/partials are deliberately
  unsupported: a skill is one readable file, and its full prompt cost is
  visible in that file.

## 7. Templates — `templates/<type>/`

Two files per document type. `template.md` is the scaffold — front matter,
the required headings, inert `{{...}}` placeholders — copied by authors (a
`doc new` scaffolding command is a later convenience; phase 1 ships the file
as reference). `manifest.yaml` drives validation (DESIGN-003 §3) and binds the
type's workflow:

```yaml
type: spec                     # must match the directory name
reviewer_role: spec-reviewer   # role dispatched on submit (DESIGN-003 §4)
front_matter:
  required: [title, type, owner]
sections:
  order: strict                # strict: required headings appear in this order
                               # any: presence only
  required:
    - heading: Overview
    - heading: Acceptance criteria
  optional:
    - heading: Open questions
rules:
  - kind: min_list_items
    section: Acceptance criteria
    min: 1
```

Semantics:

- Heading match is case-insensitive on heading text at any level; a rule or
  section entry may pin `level:` when it matters.
- **The validation floor is not configurable.** Checks 1, 3, and 4 from
  DESIGN-003 §3 (front matter well-formed and `type` agreeing with the
  manifest; internal links resolve; no unresolved placeholders) always run.
  Manifests configure only check 2 (sections) and check 5 (type-specific
  rules). Every document type meets a minimum bar no matter how its manifest
  is edited.

  > **Note, 2026-09-28 (Sam, accepted with
  > [SPEC-019](../specs/SPEC-019-bugs.md) FR-1.4, choice 18).** Check 4
  > ignores `{{…}}` and `TODO` inside fenced code, for every document type.
  > Fenced code is quoted material, so a log line or a snippet of template
  > braces isn't an unresolved placeholder.
- **Rule kinds are a Go registry**, mirroring the gate catalogue pattern
  (DESIGN-003 §8): a manifest references a kind by name; an unknown kind is a
  config error. Phase 1 ships `min_list_items`; phase 2 adds `table_parses`
  (the dev-plan task table). New kinds are added in code and listed here.

  > **Note, 2026-09-28 (Sam, accepted with
  > [SPEC-018](../specs/SPEC-018-decisions.md) FR-1.2 and FR-3.3).** Two rule
  > kinds join the registry: `max_words` (a field, a section or the body) and
  > `one_line` (a field). A decision's amendment is held to the floor checks
  > only in what it adds.

  > **Note, 2026-09-28 (Sam, accepted with
  > [SPEC-019](../specs/SPEC-019-bugs.md) SD-5, choice 5).** A third kind,
  > `contains_text`, takes a `section:` and a `text:`. It passes when a list
  > item in that section starts with the text, ignoring case and spacing; the
  > item may run on. The text inside another item doesn't count. A bug
  > report's manifest uses it to keep "The defect no longer reproduces" among
  > its acceptance criteria.

## 8. Pack lock — `pack.lock.yaml`

The provenance record that makes upgrade's three-way classification
(vision §12) computable without merge tooling:

```yaml
pack_version: 0.1.0            # starter-pack version that last wrote this file
files:
  - path: roles/spec-reviewer.yaml
    shipped_sha256: 9f2c…      # hash of the file as shipped, at copy time
  - path: skills/review-spec/SKILL.md
    shipped_sha256: 04aa…
  - path: templates/spec/template.md
    shipped_sha256: 77b1…
  - path: templates/spec/manifest.yaml
    shipped_sha256: c3d8…
```

Written by `init` and `upgrade`, committed to git, never hand-edited. For each
file in a newer pack, `upgrade` classifies:

| Observation | Classification | Action |
|---|---|---|
| Not in lock, not on disk | New default | Offer to copy in |
| On disk, hash == recorded `shipped_sha256`, new pack differs | Unmodified default with upstream change | Show diff; user decides |
| On disk, hash != recorded `shipped_sha256` | User-customised | Leave alone; surface that an upstream version exists |

Files on disk that appear in neither the lock nor the pack are the user's own
work and are never touched.

`config.yaml` is **not** pack-tracked: `init` generates it (connection env-var
name, budget defaults, model registry with current prices) and it is
user-owned from birth. Its `version:` field lets `upgrade` detect a stale
config *format*; the fix is proposed as a diff the user confirms — never
applied silently (vision §12: no automatic merge, no silent overwrites).

## 9. Loading and error handling

- **At `serve` boot:** every file in the compartment is loaded and
  schema-validated; any failure aborts startup with a message naming the
  file, the field, and the reason. `cromwell status` re-runs the same load
  and reports config health — editing config has a check loop with no new
  command (this is part of FR-1.1's "healthy install" report).
- **Per dispatch:** the role, its skill, and the relevant manifest are
  re-read (DESIGN-002 O-6). A load or validation failure here is
  deterministic, so it skips the retry policy: the dispatch fails immediately
  and raises a checkpoint of kind `config-error` naming the file — distinct
  from `dispatch-failure`, whose retries imply transience (F-8).
- **Cross-file references** — role → model, `routing` → model, manifest →
  role, role → skill, `commands` entries → tool names — are resolved at load;
  a dangling reference is a config error handled by the two paths above.

## 10. Phase-1 starter pack

`init` ships exactly:

| File | Origin |
|---|---|
| `config.yaml` | Generated: `database.url_env`, anthropic provider, model registry with current prices, budget defaults |
| `.gitignore` | Static: `run/` |
| `pack.lock.yaml` | Generated: hashes of the four pack files below |
| `roles/spec-reviewer.yaml` | Pack |
| `skills/review-spec/SKILL.md` | Pack |
| `templates/spec/template.md` | Pack |
| `templates/spec/manifest.yaml` | Pack |

The reviewer skill and role identity drive the escalation rate — the very
signal SPEC-001's phase 1 exists to measure — so their content is drafted
during phase-1 implementation and reviewed with the same care as code, not
treated as fixture filler.

## 11. Decisions recorded here

| # | Decision | Rationale |
|---|---|---|
| F-1 | Strict parsing; unknown keys are errors | Typos fail loudly, not silently |
| F-2 | Secrets are env-var names in config, values in the environment | NFR-4 by construction |
| F-3 | Prices in USD per million tokens; snapshot at dispatch claim | Matches provider convention; O-4's exact retrospective costing |
| F-4 | Document types bind their reviewer in the template manifest; all other purposes bind in `assignments:` | The type owns its workflow; one resolution rule per purpose class, no search order |
| F-5 | Outcome tools are code, not config | The purpose contract stays machine-processable (O-2); a role edit cannot break dispatch completion |
| F-6 | Validation floor non-configurable; manifests add rules only from a registered set | Every document meets a minimum bar; rule registry mirrors the gate catalogue |
| F-7 | Pack lock records shipped hashes; `config.yaml` never pack-tracked | Three-way upgrade classification without merge tools; generated config is user-owned from birth |
| F-8 | Config errors skip retries and raise `config-error` checkpoints | Deterministic failures; retrying them is noise, and the kind name tells the human it's their file, not the provider |
| F-9 | Filename/dirname is the identifier for roles, skills, and templates | No internal `name:` field to drift out of sync |

## 12. Open questions carried forward

- `assignments:` and `commands:` are shaped here but first exercised in
  phase 2 (implementer dispatch, tool host); their schemas are provisional
  until then and may be extended without structural change.
- `tool_hints` placement in the prompt (appended to tool definitions vs a
  dedicated block) is a phase-2 prompt-assembly detail, not a format question.
