## Where it stands

Approving a design now records what we want and starts nothing. A person
presses **Send to development** on a feature, or on several from their
initiative, and the orchestrator writes and reviews the spec, writes and
reviews the plan, decomposes and estimates it, and stops at **Start building**.
Specs are reviewed as DEC-006 Amendment 1 says: the agent reviewer approves,
humans raise issues that must be answered, a hold is optional, and no setting
lets a spec through unreviewed. The chat agent can carry a person's verdict,
issue, review request or release, quoting them, and nothing more.

## What was built

**The sent mark** (`feature_sends`): who sent a feature, when, and the send's
hold. It is a mark, not a state. A feature being built counts as sent.

**The trigger.** Both authoring invariants, and a new estimate step, need the
mark. Design approval, feature creation and description only re-check. Send is
the trigger. The heartbeat sweep covers sent features only. The cascade still
retires specs for every feature (SPEC-009 FR-9.1 and FR-9.2 unchanged), and
rewrites them only for sent ones.

**The revise loop,** which SPEC-009 as built didn't have: a spec or plan sent
back to draft now goes back to its author agent, with the draft, the findings
and the human issues in its prompt. It is part of the invariant, so Send and
the sweep pick it up too. It is bounded by `dispatch.max_review_rounds`; at the
cap an `authoring-deadlock` question in the Inbox offers one more round.

**Spec review** under Amendment 1:
- `config.yaml` gains `spec_review: {agent: true, hold: false}`. With `agent:
  false` every spec waits for a person, whatever else is set.
- The hold (project default, per-send override on the send screen) holds an
  agent's *approval*; a send-back goes straight to the author.
- On the document page, and by relay: **approve it myself**, **send it back**,
  **raise an issue**, **ask for an agent review**, **let the reviewer decide**.

**Human issues** are rows in `document_comments` with `is_issue`. The
reviewer's `submit_review` gains an `issues` list, and an approval must answer
every open issue `addressed` or `does_not_apply`, with a note. That is checked
inside the reviewer's turn. Where an issue goes depends on the document and the
feature (SPEC-011 FR-6.2).

**Send to development** in the web UI: a primary button on the feature page,
**Send features to development…** on an initiative, and the send screen with
features, steps, roles and models, what is already done, who reviews each spec,
a forecast or "no forecast yet", free slots, and the hold. **Withdraw** while
nothing has started.

**The document page** gains Submit, Revise and Detach.

**The design reviewer is retired** from the starter pack; its skill is now
`.cromwell/chat-skills/review-design/SKILL.md`, reworded for a chat AI.

**The starter pack** ships `write-spec` and `write-dev-plan` switched on, and
the `spec_review` block.

**Gate 2** reads **Start building**.

**MCP**: `relay_verdict`, `relay_issue`, `relay_review_request` and
`relay_release_hold`, in `internal/server/mcp_relay.go`. Each requires the
person's words in `quote`, and audits `via: mcp` with it.

## Decisions taken, and the eight for Sam

The spec's SD-1 to SD-16 record them all. **These need Sam's explicit yes**
(SPEC-011 DoD 7):

1. **Withdraw is built, small** (SD-10). It is allowed while every authoring
   dispatch since the send is still queued. Once an agent has started, Abandon
   is the way out. Worth having because sends wait in the queue when slots are
   full, which is when a person may change their mind.
2. **The mark governs the plan and the estimate too, and a `ready` feature can
   be sent** (SD-2, SD-3). "Nothing runs before Send" needs it. Building counts
   as sent, so a feature started before M3 still gets its spec rewritten on a
   design revision.
3. **The hold catches approvals only** (SD-5). Holding a send-back would only
   delay the fix.
4. **Existing projects keep their design reviewer** (SD-8). Config is strict
   and authoritative; silently ignoring a line a project wrote is the drift the
   strict parser exists to prevent. It comments and never rules. Delete
   `reviewer_role:` from `templates/design/manifest.yaml` to retire it.
5. **How an issue is marked addressed** (SD-6), and **an issue on an approved
   spec opens a successor** rather than retiring the spec at once (SD-7), as
   DESIGN-010 §5 describes.
6. **Start building stays reachable from the CLI and `POST /api/features/start`**
   until DEC-003 retires them (SD-16). DESIGN-010 §5 says web UI only; this
   milestone doesn't own the CLI.
7. **Issues on approved plans are supported**, with re-decomposition of a
   successor plan on a `ready` feature (SD-14).
8. **A "send back" of a spec is a human issue plus a return to draft** (SD-15),
   from the UI, by relay, or on an escalation.

Other decisions a reader should not undo:

- **The review round cap is shared** with code review (`max_review_rounds`).
- **Each submission gets its own review**, keyed by its submission time: an
  author who resubmits unchanged text must still be reviewed, or the loop
  stalls. A verdict applies only to the content it reviewed.
- **Enqueueing an author dispatch locks the feature row** and refuses a second
  live one. An event and the sweep found the same gap at once in testing.
- **G0 reads the approved design in force**, not the newest document, so an
  open revision doesn't make every feature unsendable (a walkthrough finding).
- **Any approval with no agent review behind it is a person's**, and settles
  the open issues, whether direct or on an escalation.
- **An author never writes over a file it didn't register**: a detached draft
  left on disk is kept, and the authored one goes beside it (`spec-2.md`).
- **Settings are read live, the hold is fixed at the send.** Turning agent
  review off applies to work already sent from its next submission.

## The live smoke checklist, for Sam

Needs an AI provider key. Uses `scripts/smoke-project.sh` (its closing
instructions now describe this flow).

```
eval "$(CLAUDE_CODE_REMOTE=true scripts/test-db.sh)"   # or set SMOKE_DATABASE_URL
SMOKE_FORCE=1 scripts/smoke-project.sh
export CROMWELL_DATABASE_URL=...   # printed by the script
export DEEPSEEK_API_KEY=...        # or your provider's
cd /tmp/cromwell-smoke && /tmp/cromwell serve
```

In a second terminal, as the script prints: `initiative add greet`,
`feature add greet/time` **with a description**, `doc add` the design, and
`submit` it.

**The main smoke** (DoD 4):

1. Open the design's page. There are no agent comments: it waits for you.
   Approve it.
2. **See nothing start**: Home shows no running or queued work, and the
   feature's page offers **Send to development**.
3. Press **Send to development**. The send screen shows the steps with the
   provider's model, who reviews the spec, "no forecast yet" on a fresh
   project, and four free slots. Leave the hold off. Send.
4. Watch, on the feature's page and the Home queue: `write-spec`, then
   `review-spec` (approved, or sent back and revised — both are fine), then
   `write-dev-plan`, `review-dev_plan`, decomposition, and `estimate`.
5. **It stops**: the feature is **Ready to start**, the page shows **Start
   building**, the rail shows the estimate, and no `implement-task` runs.
6. Record the tokens per step (Work page, or `SELECT purpose,
   input_tokens + output_tokens FROM dispatches`) in a walkthrough, as
   SPEC-009's live run did.

**Optional, the hold:** on a second feature, tick the hold on the send screen.
After the spec review the spec's page says it is waiting for you. Try
**Raise an issue** first (watch the author revise and the reviewer answer the
issue), then **Let the reviewer decide**.

**The cascade smoke** (SPEC-009 DoD 3, in the same session):

1. On the approved design's page press **Revise**, edit
   `docs/greet/time/design.rev.md` (add a decision), commit, and press
   **Submit for review** on its page, then **Approve**.
2. With one sent feature, no checkpoint is raised: its spec (and plan) are
   **superseded** and archived under `docs/_superseded/`, the feature returns
   to `idea`, and `write-spec` runs again against the revised design, through
   to Start building.
3. If you sent two features first, one `design-revision` question appears in
   the Inbox listing both specs; answer it per spec.

## Traps for the next session

- **Migration order.** `0007` is M3's; M6 has `0008`. The runner only applies
  versions above the highest applied, so if M6 merges first, `0007` never runs.
- **`TestMCPAdvertisedToolSetIsExactlyTheAuthoringSet`** now names the four
  relay tools. Any later relay tool (M5's tick-a-job) needs a decision and an
  entry there.
- **The mock provider's FIFO** is consumed by whatever dispatch runs next. The
  starter now enables `write-dev-plan` and `estimate`, so a test that approves a
  spec or plan on a *sent* feature must script those or switch them off
  (`h.onlyWriteSpec()`, `h.editConfig(...)`). Unsent features dispatch nothing.
  To learn an issue's id before scripting its answer, pause the author
  (`h.pauseAuthor()`), raise the issue, script, `h.resumeAuthor()`, and run
  the sweep.
- **`#doc-live` needs `hx-disinherit="*"`.** Without it, any form inside the
  document page's live block replaces the whole page on submit.
- **`pkill -f "cromwell-m3 serve"`** in `setup.sh` matches any shell whose
  command line contains that text. Run the script as a file, not inline.
- **A project served from a long path won't start** (the unix socket's
  108-byte limit), as M4 found. The demo uses `/tmp/m3demo.sock`.
- **Projects made before M3** have `write-spec`/`write-dev-plan` commented
  out, so Send writes a mark and nothing is written. The send screen warns
  "Nobody is assigned…". Uncomment them in `config.yaml`. A feature part-way
  through the July chain (spec approved, plan not written) waits until it is
  sent.
