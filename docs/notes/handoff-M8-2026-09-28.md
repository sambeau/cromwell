## Where it stands

Every initiative, feature, milestone, roadmap and task has an ID minted by the
database: `INIT-001`, `FEAT-003`, `MS-002`, `RM-001`, `FEAT-003-T04`.
Checklists get `CL-` IDs as soon as M5's table exists. Documents Subutai writes
carry `id:` and `revision:` in their front matter. When a file is moved or
renamed and committed, the server follows the ID to the new path, so **moving a
file on disk doesn't detach it**, which is the roadmap's test.

Existing files are adopted where they sit, from the web UI or over MCP, and
this repository's own DEC-001 to DEC-007 adopt without renumbering. Creating an
initiative or feature, in the UI or over MCP, starts its design document in
`docs/work/<INIT-ID>-<slug>/`. IDs appear in titles, headers, breadcrumbs,
lists and MCP results, and `/ui/id/<ID>` goes to anything by its ID.

The suite is green and the browser demo ran with no AI provider.

## What was built

**Minting (SPEC-015 FR-1, FR-2).**

- One Postgres sequence per prefix, and a column default,
  `mint_ident('FEAT')`, on each entity table. Every insert gets an ID whatever
  code path made it, including M5's checklist inserts, which know nothing
  about IDs.
- The registry is `internal/ident`. `BUG`, `SPK` and `CL` are reserved there
  with their sequences made, so a bug table later needs only its column
  default. A test checks the registry and the database agree.
- Tasks take their feature's ID and a number from the feature's own counter,
  `features.task_seq`, bumped in the same statement that inserts the task.
- `0010` numbers existing rows in creation order (roadmaps by UUIDv7 row id,
  since they have no `created_at`) and moves each sequence past them.

**Document IDs and revisions (FR-3).**

- A document's ID is its owner's ID plus its type: `FEAT-003-spec`,
  `INIT-001-design-2`, `PROJECT-note`. A decision is `DEC-nnn`.
- Subutai writes `id:` and `revision:` into the front matter as text, keeping
  everything else byte for byte (CRLF, BOM, comments, key order).
- Revise gives the successor the same ID at the next revision. Approval
  archives the old revision as `docs/_superseded/<ID>.r<n>.md`. Documents with
  no ID archive as before.
- Authored specs and plans get IDs. A feature made since `0010` keeps them in
  its initiative's folder; one made before keeps SPEC-009's paths
  (`features.legacy_doc_paths`).

**Identity lives in front matter (FR-4).**

- On each commit, the Markdown files it touched are read. A file carrying a
  registered document's ID and revision at a new path moves that document's
  row there, audited as `document.moved`.
- The rules: a registered path is never taken over, a copy isn't a move, and
  the database is the record.
- The same check runs at boot and on every heartbeat, so moves that arrive by
  pull, merge or rebase are followed too. A document still missing is looked
  for again only when `HEAD` moves.
- A moved document's old page address redirects. A page whose file lost its
  `id:` line says so.

**Adopt (FR-5).**

- `AdoptDocument` serves both surfaces: **Adopt a file…** on the project,
  initiative and feature pages, *Give it an ID* on a document known only by
  its path, and the MCP tool `adopt_document`.
- It writes the two lines, re-records the hash in the same transaction, and
  commits the change on its own as `subutai`, so nothing reads it as drift.
- Approved adoption is for designs and the types with no template, in the UI
  only, and records the person's verdict. Over MCP it adopts drafts only.
- Every refusal is a sentence (SD-11).

**Creating work creates its documents (FR-6).**

- The create dialogs and `create_initiative` and `create_feature` start a
  design from the template, registered, attached and committed, unless opted
  out.
- An untouched starter gives way to a design attached or adopted after it.
- The HTTP API and CLI don't start one.

**Showing IDs (FR-7).**

- IDs appear in titles, headers, breadcrumbs, child lists, the documents
  page, the work list and Home, and in MCP results. A document result's `id`
  is now its ID, and its row id moved to `row_id`.
- MCP tools in `mcp.go` take an initiative's or feature's ID wherever they
  take its path, written in capitals. The milestone and roadmap lookups take
  `MS-` and `RM-` IDs.

## What needs Sam

**1. Approve SPEC-015.** The review found eight material problems in the first
draft. The biggest were:

- adopting as approved skipped every check the other routes to `approved`
  have;
- a second live spec would silently become the contract;
- writing IDs into approved documents needed saying as a sanctioned
  exception;
- `0009` arriving after `0010` would leave checklists without IDs;
- adopted drafts of untemplated types could never be approved.

All are fixed in the spec and the code; SPEC-015 §7 maps each finding.

**2. Fifteen choices** (SPEC-015 DoD 8). In short:

1. project documents are `PROJECT-<type>`;
2. MCP adopts drafts only;
3. adopt refuses uncommitted files;
4. Attach stays path-only;
5. Detach takes the ID out of the file, committing when clean;
6. starter designs on by default, for features too;
7. no starter from the API or CLI;
8. existing features keep SPEC-009's paths;
9. the folder is derived, not stored;
10. approved adoption only for designs and untemplated types, in the UI;
11. one live spec or plan per feature, and an untouched starter gives way;
12. the identity lines are the one sanctioned change to an approved document,
    and chat may make it;
13. *This was already approved* for adopted untemplated drafts, UI only;
14. a foreign `id:` is refused;
15. the checklist step runs on every migration.

## Decisions taken in the build

- **An ID is a column default, not application code or a trigger.** It can't
  be skipped, it needs no change to M5's code, and DESIGN-001 §2.4 keeps
  triggers for bookkeeping.
- **The identity editor is its own small parser** (`internal/content/identity.go`),
  not `config.SplitFrontMatter`. That one doesn't recognise CRLF or a BOM, so
  it would have added a second front-matter block to such files (R15-8).
- **A decision whose file name claims a number already taken is refused**, not
  given a new number. `DEC-005-again.md` adopted as `DEC-009` would contradict
  its own name. SPEC-015 FR-5.4 was updated to say so.
- **A title that already starts with its ID isn't prefixed again.** A
  decision's heading is "DEC-005: …", which would otherwise read
  "DEC-005 DEC-005: …".
- **MCP document results changed shape.** `id` is the document's ID and
  `row_id` the old UUID. Nothing in the suite read the old `id`, and the relay
  tools take a path.
- **Detach's inner method now reports what happened to the ID**
  (`detachDocument`); `DetachDocument` keeps its signature.

## Where the brief conflicted with an approved document, or went further

- **Writing into approved documents.** DESIGN-003 L-2 makes approved documents
  immutable, and DESIGN-010 §11 says an accepted decision is never edited. The
  brief and DESIGN-010 §7 ask for adopt to write IDs into existing files,
  which include approved ones. DESIGN-010 §7 is the later approved design and
  provides for this ("touching only its front matter"). So SPEC-015 SD-11
  states it as the one sanctioned exception, with its safeguards, and asks Sam
  to confirm it (choice 12).
- **"MCP tools that take a path should also accept an ID."** The relay tools
  are in `mcp_relay.go`, and the milestone and roadmap tools' results in
  `mcp_plan_tools.go`, both M5's files. They accept or show IDs only as far as
  shared lookups allow (SD-19). The rest is a follow-up after M5 merges.
- **"Adopting a file whose name carries a well-formed ID keeps that ID."** It
  does, unless another document already has the number. Then it refuses,
  rather than contradicting the name (above).
- **Spec before code.** The minting foundations (the migration, `ident`, the
  editor) were built while the independent review ran, as M3 did. Every
  review finding was applied to the code afterwards, and nothing merged or
  was approved before the review.
- **The spec said the server migrates at boot.** It doesn't: only `init` and
  the test harness run the migrator. SPEC-015 SD-20 was corrected. Any
  database that later receives `0009` must run the migrator, and that run
  also gives checklists their IDs.

## Traps for the next session

- **Migration order with M5.** On the merged line `0009` runs before `0010`.
  A database made from this branch alone has `0010` and no `0009`. The next
  `init`, or test run, applies `0009`, and `attachLateTables` then numbers the
  checklists. Don't remove that call when merging `migrate.go`.
- **Tests that create through the UI or MCP now get a starter design.** A test
  that then counts a feature's documents, or expects its attached design to be
  the body, has to allow for it. Opt out with `start_design_offered=1` and no
  `start_design` in a form, or `design_document: false` over MCP.
- **The harness's hook is `/usr/bin/true`.** Tests call `srv.OnPostCommit`
  after a commit to stand in for the hook. The demo's hook is real.
- **`gofmt -l` still lists three files** (`internal/lifecycle/task_test.go`,
  `internal/server/integration_send_test.go`, `internal/toolhost/toolhost.go`).
  They were unformatted before M8.
- **A project served from a long path won't start** (the 108-byte socket
  limit). The demo used `/var/tmp/m8demo`. `setup.sh` stops a previous demo
  server by the process id it saved, never with `pkill -f`.
