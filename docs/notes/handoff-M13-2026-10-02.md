## Where it stands

A person or the chat agent can now do a task's work through the front door,
and nobody's work escapes its judges.

- **Over MCP:** the chat agent finds a task with `get_feature`, claims it with
  `claim_task`, works in the feature's working copy, and hands it in with
  `submit_task`. The claim returns the working copy and the contract: the
  spec, the plan, the task and the surfaced decisions.
- **In the web UI:** a person does the same from the task's page.
- **Judging:** submitting is the only way forward. It commits the work and
  queues the same dispatched code review an agent's work gets. A send-back
  returns the task to its claimant. The dispatched verifier still verifies
  the feature.
- **The executor record:** every round of every task records its executor
  (an agent with its role and model, the chat agent, or a person). It is
  shown on the task page, the feature's new task list, the timeline and MCP.
- **Expiry:** a claim nobody touches for 24 hours asks a person "Is someone
  still working on it?".
- **Unclaimed commits:** a commit on a feature's branch that Subutai didn't
  make, while nobody held a claim, raises a notice.
- **Unmeasured tokens:** chat and human work is *unmeasured*, not zero.
  Calibration and forecasting leave it out.
- **The reviewer:** by default, the chat agent's work is reviewed with the
  most expensive configured model.

**The roadmap's done-when** is "a task done in chat gets the same review and
verification as an agent's". It is one test,
`TestChatClaimedTaskIsReviewedAndVerifiedLikeAnAgents`, and it passes. The
suite is green with the race detector. The browser demo ran with no AI
provider.

## What was built

**The execution record (FR-1).** `executions` has one row per executor's
part in a round of a task: `agent` (with its role, model and run), `chat` or
`person` (with the claim). It uses SPEC-017's vocabulary, and one function,
`executorLine`, built on `whoWords`, says it everywhere:
- "Implemented by the chat agent."
- "Being implemented by sam, who claimed it just now."
- "Implemented by the implementer (claude-sonnet-5), from work the chat agent
  started."

The migration backfills agent rows from the `dispatch.running` audit rows.

**Claims (FR-2).** `work_claims` records each claim, and `lifecycle/claim.go`
is the claim's state machine: `open`, `submitted`, `returned` and `ended`.

- **What a claim can take:** a ready task, or an active task that no agent is
  running. Claiming an active task cancels its queued or failed dispatches
  and withdraws its `dispatch-failure` question.
- **One hand in a working copy:** an open claim holds the feature's working
  copy, and the governor holds the feature's implementers while it is open.
- **Send-back:** it returns the claim as `returned`. The claim holds the task
  but not the copy, until the claimant resumes it.
- **Release:** a person's act. It commits what was left and queues an agent.
- **Endings:** a claim ends with its task's approval or abandonment, or its
  feature's abandonment, at all three sites, through
  `store.TransitionFeature`.
- **Races:**
  - one lock order everywhere: the feature, then the task, then the dispatch;
  - `StartImplementDispatch` re-checks under the feature's lock;
  - `TransitionTask` has a state guard;
  - a per-working-copy lock serialises git;
  - a 15-minute "completion pending" hold covers the moment between an
    implementer's success and its commit.
- **For M14:** the `claimable` interface keeps spikes out of M13's code
  (FR-2.10).

**MCP (FR-3, FR-6, FR-9).**
- `claim_task` and `submit_task`, with the rules in their descriptions and
  results.
- `get_feature` gains `tasks`, each with its executor, claim, `claimable`,
  `why_not` and review comments.
- The `initialize` instructions gain two sentences.
- `chat-skills/work-a-task/SKILL.md` is new. A test checks it carries every
  rule the claim's result gives.
- `TestMCPAdvertisedToolSetIsExactlyTheAuthoringSet` names the two tools on
  purpose. Its must-not-exist list gains eleven names, among them
  `release_task`, `approve_task`, `verify_feature` and
  `submit_implementation`.

**The web UI (FR-1.5 to FR-1.7, FR-4).**
- The task page gains the executor line and the claim panel, in six states,
  through two includes from the new `executors.html`.
- The feature page gains a task list, **Tasks in this feature**, with
  executor icons and "Claimed by" labels.
- New routes: `POST /ui/task/claim`, `/submit` and `/release`. Each is
  same-origin only, and redirects with a fixed notice.
- The timeline has "Claimed by", "Submitted by" and "Released by" moments.

**The safety nets (FR-5).**
- **The claim sweep**, on the heartbeat, sees working-copy changes as
  activity. It raises `claim-stale` on the task, with **Keep the claim** and
  **Release it to an agent**, and withdraws it on any activity.
- **The branch watch**, on the heartbeat and after every post-commit, checks
  the branches of features being built or verified. It knows Subutai's own
  commits by their recorded hashes, leaves out `main`'s commits, and catches
  a rewritten branch. It raises `unclaimed-commit` on the feature, with **I've
  seen this**.

**Unmeasured actuals (FR-7).**
- **What is unmeasured:** a task with a chat or person execution; a feature
  with such a task, or whose spec or plan was last written in chat or by a
  person; and an initiative with either.
- **Calibration:** `RetrieveCorpus` and `RecentCalibration` filter in SQL,
  before their `LIMIT`. `PurposeTokenSamples` skips unmeasured rounds.
- **The estimate API and the CLI** say "unmeasured (at least n tokens)".
- **The rail** says "Not measured: …".

**The reviewer (FR-8).** `claims.chat_review_model` sets it:
- absent: the priciest configured model;
- `same`: the reviewer's usual model;
- a name: that model.

It applies to code reviews of chat-implemented tasks, and to reviews of
specs, plans and bug reports the chat agent last wrote. The task page names
it only when the chat rule actually changed the model. The rule is recorded
on the submission.

**The implementer now sees its reviewer's comments** on rework (FR-2.12,
SD-17). This fixes a defect that predates M13.

## Decisions taken in the build

- **Claim executions are unique per claim and round,** not per claim. FR-1.1
  was written both ways; T1 found it, and the spec now says it.
- **The watched head is set at boot** for existing worktrees, because a
  migration can't run git (FR-5.9).
- **The feature page has a new task list.** No page listed a feature's tasks
  before, and the plan page lists none. FR-1.6 now says so.
- **The branch watch lists commits with `git log --no-merges`.** A merge of
  `main` into the branch isn't flagged.
- **The completion-pending hold lasts 15 minutes** after an implementer's
  success (`PendingCompletionWindow`). A completion that never commits
  can't hold a feature for ever. See bug candidate 1.
- **A code review's idempotency key includes the task's round.** Otherwise a
  resubmission of an already-reviewed commit got no review.
- **Keep on a deadline question clears the deadline,** or it would come
  straight back. Only M14 sets deadlines.
- **An approval while a claim isn't `submitted`** (a person's answer at a
  deadlock) ends the claim as `abandoned`, not `done`.
- **Commit messages name a task by its plan id** (`T1`), as the implementer's
  completion always has.

## Where the brief conflicted with an approved document, or went further

- **The brief's "verification can never be chat-executed"** and DEC-007
  decision 5 agree. There is no verification task to claim, and `claim_task`
  refuses anything that isn't a task.
- **DEC-007 decision 7's "an active feature's paths".** Features don't own
  paths, so the spec reads it as the feature's branch, watched while the
  feature is built or verified (SD-10, choice 10). A dated note is due on
  approval.
- **DEC-007 decision 10 says reviews "default to" a stronger model.** The
  first draft defaulted to no change. The spec review called that a
  departure, so the default is now the priciest configured model, with
  `same` to opt out (SD-14, choice 14).
- **DEC-004's "may not drive any development-side lifecycle transition"** is
  read, after DEC-007 decision 3, as not covering claim and submit. A dated
  note on DEC-004 is due on approval (DoD 9). DEC-005's "direct a dispatch"
  likewise doesn't cover a claim cancelling a queued dispatch (SD-15).
- **The brief asks the reviewer model to apply "when the executor is the chat
  AI".** SPEC-017 §6 had already named M13 for chat-written documents too, so
  the setting covers both (SD-14).
- **The brief says spikes are out of scope** but claims must serve them.
  `work_claims` and `executions` are keyed on `ref_type`, and the claim
  service runs through an interface. M14 adds `spike` to the `ref_type` enum
  in `0015`.

## Bug-report candidates (minor findings, for M12's triage queue)

From the reviews, after the fixes. Each is minor; none blocks the merge.

1. **A completion that never commits is handed over silently** (round 2
   B14). If an implementer's completion fails for good, for example with a
   configuration error, the 15-minute hold ends with nobody told. A sibling's
   implementer or claim then commits the stranded work as its own. This
   isn't a regression: before M13 the hand-over was immediate.
2. **A `dispatch-failure` question can still be raised** about a task a claim
   took a moment earlier (round 2 B15). *Cancel* then only logs an error.
3. **A batch's base commit is stale for agents** (SPEC-020 §7). Each later
   task's code review diffs its siblings' work too.
4. **The revision-in-flight *pause* answer** clears `spec_stale` exactly as
   *continue* does, so a pause doesn't hold (SPEC-020 §7).
5. **The timeline says "A person decided: keep"**, the answer's raw word,
   for a `claim-stale` answer. `answerWords` needs the three new answers.
6. **The end-to-end test's assertions are weaker than the spec** in two
   places (round 2 B19). It doesn't check that T02's implementer runs while
   T01 is in review. Its FR-6.4 check accepts any answered question on the
   task.
7. **Test organisation** (quality Q11, Q22): shared helpers live in
   feature-named test files, and `integration_claims_round1_test.go` is
   named by when it was written.
8. **`claimLocked` and `watchBranchLocked` are long** (Q10), and the new sweep
   code logs little (Q12).
9. **Small tidy-ups** (Q16 to Q18, Q21, Q23, Q24): a one-argument
   `refusal()`, an inverted empty branch, duplicated counts, an ignored
   `Scan` error, and comment placement.
10. **`claimOrNil` swallows every error** (Q7, accepted with a comment).

## A live smoke checklist for Sam

With a real provider, on the smoke project:

1. In chat, ask the agent to claim a task of a feature being built, make the
   change, and submit. Check the review runs on the stronger model, and that
   the task page says the chat agent implemented it.
2. Have the reviewer send something back. Check it returns to the chat agent,
   and that `get_feature` shows the comments.

   notice.
5. Check the estimate of a feature done partly in chat reads "unmeasured".

## Traps for the next session

- **`store.TransitionTask` now refuses a stale state** with `ErrStaleState`.
  A caller that read the task earlier and transitions it later may have lost
  a race. Treat that as "someone else moved it", not as a crash.
- **An implement dispatch starts through `StartImplementDispatch`,** which
  may cancel it (the task is claimed) or keep it queued with a reason. Don't
  call `MarkDispatchRunning` for `implement-task`.
- **Git in a feature's working copy goes through `withWorkingCopy`.** The
  lock isn't re-entrant: code already holding it calls the `…Locked`
  variants, e.g. `watchBranchLocked`.
- **Every commit Subutai makes on a feature's branch must be recorded** with
  `store.RecordWorktreeCommit`, or the branch watch reports it as unclaimed.
- **A code review's idempotency key includes the round**
  (`rules.CodeReviewIdempotencyKey(task, commit, round)`).
- **Parallel test runs need separate Postgres clusters.**
- **A project served from a long path won't start** (the 108-byte socket
  limit). The demo used `/var/tmp/m13demo`, on port 8820.
- **Test clusters started by agents** under `/var/tmp/pgdata-*` were all stopped
  at the end; `pg_ctl` refuses to run as root here, so they were stopped by
  sending SIGINT to the PID in each `postmaster.pid`.
