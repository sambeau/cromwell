## Where it stands

A person can edit any draft document in the browser. Press **Edit** on its
page, change the Markdown with a live preview beside it, and press **Save &
commit** or **Save**.

- **Save & commit** writes the file and commits it alone. The configured
  operator is the author and `subutai` the committer.
- **Save** writes the file and leaves the commit to the person.
- **A browser save never overwrites a change made on disk, and a change on
  disk never throws away what the person typed.** A save that finds the file
  changed stops, shows both sides as line diffs, and keeps the text to copy.
- **The editor always shows the document's state:**
  - a draft is edited in place;
  - a document under review goes back to draft when saved;
  - an approved one starts a revision, through the existing Revise, and the
    revision takes the original's place when approved.
- **Refusals:** the editor stands aside while an author agent is at work on the
  document or due to revise it, and where a question in the Inbox governs the
  document. It won't save a text that breaks the `id:` and `revision:` lines.
- **Warnings:** it warns, in sentences that say what will happen, when a
  document feeds work in flight.

The suite is green, and the browser demo ran with no AI provider.

## What was built

**The editor (SPEC-016 FR-1).**

- `GET /ui/edit/<path>` shows a monospaced textarea holding the whole file,
  front matter included, beside a preview rendered by the document page's own
  goldmark and bluemonday renderer. It updates as you type, through
  `POST /ui/edit/preview`.
- No library is vendored. `editor.js`, delegated like `dialog.js`, adds three
  things:
  - Ctrl-S or ⌘-S to save;
  - **Copy your text**;
  - a question before a link or boosted request leaves unsaved text.
- Line endings and a byte-order mark are restored to the file's own on save,
  and the template keeps a file's leading blank line.

**Save and Save & commit (FR-2).**

- `SaveEdit` in `internal/server/edit.go` serves both.
- Save & commit runs `git add` and then `git commit --only -- <path>`. The
  author is `ui_actor`, as `Name <name@localhost>` unless it is written with an
  email. The committer is set to `subutai` through the environment, so it works
  in a repository with no git identity.
- The message is "Edit <ID> in the browser", with the path, state, revision and
  operator in the body. A subject of the person's own replaces the first line.
- A refused commit unstages the path and says why.
- Save & commit refuses a file that holds uncommitted changes Subutai didn't
  write. "Subutai's" means the editor's last save over a clean base, or
  Revise's working copy, each known by a hash on the audit trail.

**Locking (FR-3).**

- The form carries:
  - the row id;
  - the base's hash;
  - the state and path it showed;
  - the base itself, for the diff.
- A save refuses a changed state or path, then, under a mutex, a changed hash.
- It writes to a temporary file and renames it into place.
- The conflict page shows "what changed on disk" and "what you changed" and
  keeps the text. It offers **Copy your text** and **Reload from disk**, and no
  "save anyway".
- A ten-second freshness check warns before the save.

**The lifecycle (FR-4).**

- **A reviewing document** is withdrawn to draft on save, in one transaction
  that also cancels queued reviews and clears a hold, using the lifecycle's
  existing `withdraw` event.
- **An approved document** gets an explanation page with **Start a revision
  and edit it**, which runs `ReviseDoc`. An open revision is edited instead.
- **Refused:**
  - superseded documents;
  - approved decisions and approved documents of untemplated types;
  - a document the author agent is at work on;
  - a sent feature's draft that waits for its author, unless the Inbox asks
    about another round;
  - a reviewing document under a pending Inbox question;
  - a revised spec whose feature has a revision-in-flight question.
- **Warnings** cover:
  - a sent feature;
  - a feature being built;
  - an approved or revised design that sent features build from;
  - an unsent feature's draft with findings;
  - a draft under an authoring-deadlock question.

**Identity (FR-5).** A save must keep `id:` and `revision:` at their values.
The lines may move. A document with no ID can't gain one here, but can have a
foreign `id:` corrected.

**Reindexing (FR-6).** Every save publishes the watcher's own
`document.file_changed`, so the rule engine reindexes at once, with or without
a commit.

**The document page (FR-7).** The "written in your own editor" banner is
replaced by one include, `doc-edit` in `edit.html`. It holds the Edit button,
labelled by state. That is the page's only change.

**Repairs (SD-13, SD-17 to SD-19),** each small and marked with a SPEC-016
comment:

- **The approval takeover** (`takeOverCanonicalPath`) stages the working copy
  and commits only the moved paths. Before, it failed on an uncommitted working
  copy, committed the index's older text, and swept in anything staged.
- **`contractBodies`** reads the approved spec and plan. Before, task prompts
  read an open revision's draft.
- **`content.Parse`** reads CRLF and a byte-order mark. A file that can't be
  parsed still has its hash recorded (`store.RecordContentHash`).
- **`document.revision_created`** audit rows carry the working copy's `hash`.
- **The document page's Revise** gains the editor's refusals for decisions and
  untemplated types.

**Security (SD-20).**

- The editor's posts refuse `Sec-Fetch-Site: cross-site` or a foreign
  `Origin` with `403`.
- The file written must be a regular file whose directory resolves inside the
  repository.

## What needs Sam

**1. Approve SPEC-016.** The review found eleven material
problems in the first draft. The biggest were:

- a revision edited in the browser couldn't be approved: the takeover's
  `git mv` failed on the uncommitted working copy, and its commit swept in the
  index;
- the lock covered the text but not the state, so a save could withdraw a
  document submitted meanwhile, or write into one approved meanwhile;
- editing a sent feature's draft that waits for its author set the author off
  to rewrite it;
- task prompts read an open revision's draft, so the "being built" warning was
  false;
- the leave warning couldn't work, because every page is boosted;
- cross-site forms could now write and commit files.

All are fixed in the spec and the code, with tests; SPEC-016 §7 maps each
finding.

**2. Eighteen choices** (SPEC-016 DoD 8). In short:

1. a plain textarea and our own small script; no editor library;
2. the whole file is edited, front matter included;
3. the author is `ui_actor` and the committer `subutai`, for the editor's
   commits only;
4. the commit message format, with an optional subject;
5. Save & commit refuses uncommitted changes Subutai didn't write; Save
   doesn't;
6. a conflict offers Reload and Copy, and no "save anyway";
7. saving a reviewing document withdraws it, with no issue recorded, and
   whoever edits may withdraw an agent's document;
8. the identity lines are guarded; an ID can't be added, and a foreign one may
   be corrected;
9. the editor stands aside for the author agent and for Inbox questions;
10. approved decisions and untemplated types can't be revised from the editor
    or the Revise button, until M10;
11. every save publishes the watcher's event; the heartbeat is unchanged;
12. warnings, not refusals, for work in flight;
13. editing an approved document is an explicit "Start a revision" step;
14. the old banner gives way to the edit include;
15. task prompts read the approved spec and plan;
16. a sent feature's draft that waits for its author is refused;
17. approving a revision commits only its own paths;
18. the editor refuses cross-site posts, and files outside the repository.

## Decisions taken in the build

- **The Edit button's include is self-sufficient.** It reads only the
  document and the page's existing `Actions.SuccessorURL`, so `docPageData`
  gains no field and M10's changes to the page merge cleanly.
- **The approved page's Edit link goes to the approved document's own editor
  address**, which redirects to an open revision's editor. The include needs
  no successor path.
- **A refused save re-renders rather than redirecting**, as every other act in
  the UI does. A refresh that re-posts is harmless: its base hash is out of
  date, so it stops as a conflict.
- **A stale state or path is its own refusal** (`EditStale`), shown like a
  conflict with only "what you changed", because there is no change on disk to
  show.
- **The test helper `postForm` doesn't encode**, so the editor tests post with
  `url.Values`, as a browser does, with CRLF line breaks.

## Where the brief conflicted with an approved document, or went further

- **"The existing post-commit and heartbeat paths reindex the document."** The
  post-commit hook does; the heartbeat doesn't rehash documents at all. So the
  editor publishes the watcher's event itself (SD-13). The heartbeat is
  unchanged.
- **"Editing an approved document creates a successor draft"** (DESIGN-010 §7,
  and the brief). DESIGN-010 §11 says an accepted decision is never edited, and
  it is more specific, so approved decisions are refused. Approved documents of
  untemplated types are refused too, because their successor can't be
  submitted (the M8 handoff's follow-up 3). SPEC-016 SD-12 names this as a
  departure, for Sam to confirm (choice 10).
- **"Warn before editing a document … that feeds work in flight."** For one case
  a warning would have been untrue: a sent feature's draft that waits for its
  author. The author is dispatched within a heartbeat and rewrites the edit.
  That case is refused instead (choice 16). The other cases are warnings.
- **`withdraw` belongs to the author** (DESIGN-003 §2). Saving a reviewing
  document withdraws it in the editor's name, whoever wrote it. SD-9 states
  this extension (choice 7).
- **"Refuse when the working tree has other uncommitted changes to that same
  file."** I read this as a guard on Save & commit, which would otherwise commit
  someone else's work under the operator's name. Save is allowed, because the
  person saw the whole file and Save commits nothing (SD-5, choice 5).
- **"Keep your changes to the document page to one include and a button."**
  Done. The repairs touch shared files outside the page:
  - `actions.go`, `planner.go` and `ui_send.go`;
  - `content/parse.go` and `store/documents.go`.

  None of them is on the list of files M10 owns. Each change is small and
  commented.
- **Spec before code.** The line-diff package and the first cut of `edit.go`
  were built while the independent review ran, as in M8. Every review finding
  was applied to the code afterwards, and nothing was merged or approved before
  the review.

## Follow-ups, in rough priority order

1. **Cross-site protection for every `POST /ui/*`.** The editor has it; the
   rest of the UI doesn't. It is a few lines in one middleware.
2. **The cascade's archive commit** (`archiveInvalidatedFiles`) still commits
   whatever is staged. Apply SD-18's fix.
3. **Subutai's other commits** pass only `--author`, so they fail in a
   repository with no git identity. Set the committer as the editor does.
4. **A CRLF file's document page** shows its front matter as text, because
   `config.SplitFrontMatter` accepts only LF. Parsing is fixed; the page's own
   reading is in `ui_views.go`, which M10 also touches.
5. **Once M10 lets a person rule on any document type**, drop SD-12's refusal
   for untemplated types, and let Revise make their successors.
6. **A line on the feature page** when a sent feature's spec or plan was taken
   back to draft for editing, so the stall is visible (R16-17).
7. **Appending a dated amendment to a decision** from the browser.
8. **The back button** after typing in the editor restores the previous page
   from htmx's history without asking.
