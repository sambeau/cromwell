## Where it stands

Anyone can report a bug, and a person decides whether it is fixed. A person
reports from an initiative's or feature's page; the chat agent reports with
`report_bug`; an implementer, code reviewer or verifier reports mid-task with
the `report_bug` tool and carries on; and a feature's minor code-review
findings become one bug when it merges. Every bug is `BUG-nnn`, with a report
written from the new `bug_report` template, and waits in the new **triage
queue**, which has its own count in the navigation and a line on the Inbox. A
person accepts, rejects or marks a duplicate there; the chat agent can carry
that decision with the person's words (`relay_triage`).

An accepted bug travels the feature pipeline, with no second one. It is a
feature row with `kind = 'bug'`, so the send, the review loop, the plan, the
estimate, Start building, the tasks, code review, verification, the merge,
the timeline, review health and milestones are the feature code. Acceptance
stands in for G0, Send submits the report, and the spec reviewer reviews the
report as the spec. **The roadmap's done-when — an agent-filed bug is
triaged, fixed and verified — is one test,
`TestAgentFiledBugIsTriagedFixedAndVerified`, and it passes.**

The suite is green with the race detector, and the browser demo ran with no
AI provider.

## What was built

**The bug entity (FR-1).**

- `features.kind` (`feature` or `bug`) and a check that ties it to the ID's
  prefix. A bug's insert takes `mint_ident('BUG')`; the column default stays
  `FEAT`. Its slug is its ID, `bug-007`, and a feature may not take a slug
  like that.
- `bugs`, one row per bug: origin, reporter (person, chat, agent or review,
  with the run), triage, and the decision (who, how, reason, quote). The
  database refuses a relayed decision without a quote and a rejection without
  a reason.
- The report, `BUG-007-bug-report`, written from `templates/bug_report` at
  `docs/work/<INIT-ID>-<slug>/`, registered as a draft, the bug's main
  document, committed. It is filled in one pass, Steps become a numbered list,
  quoted material is fenced, and it is validated before a number is minted.
- `contains_text`, a new manifest rule: Acceptance criteria must have an item
  that starts "The defect no longer reproduces". And fenced code no longer
  counts as a placeholder or a TODO, for every document type (choice 18).
- `lifecycle.IsSpecType` and `IsContractType`, and `specTypeOf(feature)`:
  every place that asked for "the spec" now asks for the row's spec type
  (SPEC-019 Appendix A lists them all).

**Triage (FR-2).** `DecideTriage` serves the queue and the relay. Rejecting or
marking a duplicate abandons the row in the same transaction, with the reason;
a reported bug can't be abandoned round triage. The queue, `/ui/triage`, lists
reported bugs oldest first, with who reported each and what its report says,
and the three decisions; **Recently triaged** below. **Triage** in the
navigation has its own live count, and the Inbox page shows "3 bug reports
are waiting for triage." The bug's page has a triage card.

**Reporting (FR-3).** The report dialog on initiative, feature and bug pages;
`report_bug` over MCP; the `report_bug` worktree tool, capped at three per
run and refusing a duplicate title on the same origin; minor findings filed
per feature when it merges, from the audit rows each approving review writes.

**From acceptance (FR-4).** A bug's send asks its triage, its report, and
whether its origin is still being built (it waits for the merge). Send
validates and submits the report. The report's review is `review-bug_report`,
by the spec reviewer; the hold, agent review off, issues, direct approval,
send-back and *let the reviewer decide* all apply. A sent-back report is
revised in place by the spec author. Withdraw cancels a queued report review
and returns the report to draft.

**Where bugs show (FR-5).** The bug's page (the feature page, with the bug
icon), Bugs sections on initiative and feature pages, the timeline
("Reported", "Accepted in triage", "Report approved"), review health
("reviewing the bug report"), and milestones (accepted bugs only, as a
`feature` member; an initiative doesn't bring in its bugs).

**MCP (FR-6).** `report_bug`, `list_bugs`, `get_bug` and `relay_triage`, each
named in `TestMCPAdvertisedToolSetIsExactlyTheAuthoringSet`, whose
must-not-exist list gains `accept_bug`, `reject_bug`, `triage_bug` and
`send_bug`. `add_milestone_member` takes `member_type: "bug"`.

**The starter pack (FR-7).** `templates/bug_report`; `report_bug` on the
implementer, code reviewer and verifier; sections in `implement-task`,
`review-code`, `verify-feature`, `review-spec` and `write-spec`. The config
loader refuses `report_bug` on a role that can't be offered it.

## Decisions taken in the build

- **The minor findings' reporter** is the latest approving review run that
  recorded findings, since one bug gathers several reviews. Audit rows from
  before M12 don't name their run, so an older feature falls back to its
  latest code review run.
- **The triage card links to the queue** rather than repeating the three
  forms. The form still accepts a decision posted from the bug's page, and
  returns there; nothing in the UI uses that yet.
- **Filing a report commits it** as `subutai`, as a starter design is. An agent
  filing mid-run commits to the main checkout, not its worktree.
- **A rejected bug is told it was rejected**, not that it is abandoned: the
  send's readiness asks triage before state.
- **The Inbox's badge still counts checkpoints only**, so the demo's Inbox
  shows 1 (its spent budget) beside Triage's 2.
- **`feature.created` is still written for a bug**, with `kind: bug`, and the
  timeline hides it; "Reported" is the first moment. The report's writing
  isn't a moment either.

- **DESIGN-010 §9 names accept and reject.** *Duplicate* is a third outcome
  (choice 17). And §9 says triage happens in the queue; the queue is where it

  the code reviewer can use it: spec and plan reviewers are never offered

## A live smoke checklist for Sam

With a real provider, on the smoke project (`scripts/smoke-project.sh`), after
copying `templates/bug_report`, the three roles and the five skills from a
fresh `subutai init` into its `.subutai/`:

1. Report a bug on a feature from its page. See it in **Triage**, with the
   count.
2. Accept it, and send it. Watch `review-bug_report` run as the spec reviewer,
   then the plan, its review and the estimate. See that no specification is
   written.
3. Send a vague report instead (one step, "it breaks"). The spec reviewer
   should send it back; watch the spec author revise it without inventing
   steps, or ask in Notes.
4. Start building a small bug. Read the verifier's transcript: it should
   follow the steps to reproduce, or run a test that does, for "The defect no
   longer reproduces".
5. Build a feature whose code review is likely to raise minors. When it
   merges, one bug should appear listing them.
6. In chat, ask the agent to report a bug, then to reject it; check the
   quote on the bug's page.
