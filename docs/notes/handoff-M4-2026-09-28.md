## What was built

**In the web UI:**

- **An "own plan" section** on the project and on every initiative, always
  shown, with **New milestone** and **New roadmap**. The same two are in the
  "more" menu.
- **A milestone editor** in a `<dialog>` loaded by HTMX: the milestone as a
  checklist with **Take it out…** on each member, a picker that lists the
  owner's subtree and searches the whole project, and **Mark as shipped** or
  **Reopen**.
- **A roadmap editor** in the same way: a numbered list with **Up**, **Down**
  and **Take off**, and **Place a milestone** with a choice of where.
- **Add to a milestone…** on feature, initiative and milestone pages, listing
  the milestones it is in (each with **Take it out…**) and the open ones it
  could join.
- **Mark as shipped**: disabled, with G4's reason beside it, while nothing in
  the milestone is done; otherwise a sentence saying what it does and a plain
  button. A shipped milestone's editor offers **Reopen this milestone…** with
  an optional reason. The label for the stored `locked` state is now
  **Shipped** everywhere a person sees it.
- The milestone and roadmap pages open the same editors from their headers.

**Over MCP**, twelve tools: `create_milestone`, `create_roadmap`,
`add_milestone_member`, `remove_milestone_member`, `place_roadmap_entry`,
`remove_roadmap_entry`, `list_milestones`, `list_roadmaps`, `get_milestone`,
`get_roadmap`, and — added last, under DEC-004 Amendment 1 —
`mark_milestone_shipped` and `reopen_milestone`. Each is audited to the MCP
actor. The shipping tools call the same store methods as the web UI, and G4
refuses the agent in the same sentence it shows a person.

**In the store:** `CreateMilestone` and `CreateRoadmap` take an owner, and the
API still passes the project, so the CLI is unchanged. Two new mutations keep a
roadmap's positions dense and let a milestone come off one. `AddMember` refuses
to put a milestone inside itself. `MemberCandidates` feeds the picker.
`UnlockMilestone` reopens a shipped milestone: it deletes the snapshot, sets
it back to open, and writes a `milestone.unlocked` audit row with the reason
and the ids of the features the snapshot held.

**In the gate:** G4's refusal reasons are now full sentences that count
features, such as "This milestone can't be marked as shipped yet, because none
of its 3 features is done. Marking it as shipped records what actually went
out, so at least one has to be finished first." The UI, the chat agent, the
API's 409 and the audit trail all use them as they stand.

## Decided by Sam (2026-09-28)

1. **Locking is "Mark as shipped", and it can be undone** (SPEC-010 SD-11).
   Milestones are for planning and reporting, and nothing in the agent
   workflow reads them, so a permanent lock gave a mistake no remedy.
   Reopening is logged with the record it replaces. Vision §4 now carries a
   dated note saying so.
2. **Members can be taken out of a milestone from their own page, and
   milestone and roadmap pages have their own Edit button** (SD-6). Both
   depart from DESIGN-008 §5.1a, which now carries a dated note.
3. **A roadmap can include milestones that belong somewhere else** (SD-10),
   so a team can show a release it depends on without copying it. Also in the
   DESIGN-008 note.
4. **The chat agent treats milestones and roadmaps as ordinary planning, and
   may mark a milestone as shipped and reopen it** (SD-4, SD-5). This needed a
   decision, so it is recorded as
   [DEC-004 Amendment 1](../decisions/DEC-004-mcp-planning-authoring.md#amendment-1--milestones-and-roadmaps-2026-09-28):
   milestones and roadmaps are named as part of the planning layer, and G4 is
   described as a record-keeping check rather than a development gate. Every
   other gate stays out of the chat agent's reach. At Sam's request the two
   tools were then built: `mark_milestone_shipped` and `reopen_milestone`
   (SPEC-010 FR-7.10).

## Decisions taken in the build

- **The search is a plain name-and-path query, not the full-text index**
  (SD-7). The index is over document sections, so it would match entities by
  the prose of their documents, and its stemming suits prose, not slugs.
- **The response to a post is chosen by `HX-Boosted` and `from=member`**, not
  by `HX-Request` (SD-9). Every page body has `hx-boost`, so plain form posts
  arrive through HTMX too.
- **The editors need script**, as the inbox and dashboard do. The create
  dialogs and the member-side dialog are inline, like every other modal
  (SD-8).
- **G4's wording was changed at its source** rather than translated in the UI
  (review finding R10-4). The CLI's refusal message changes with it; nothing
  tested the old text, but `docs/walkthrough-phase-3.md` quotes it.
- **The list tools take `owner_type` and `owner_path`**, like
  `list_documents`. The create tools take `owner_path` alone, where leaving it
  out means the project, as `create_initiative`'s `parent_path` does.
- **An archived initiative may still own a new plan.** Nothing refuses it.

## Where the brief was wrong or went further than the design

The brief asked me to record these rather than guess.

- **"Nothing new is needed in the store except owner-scoped creation"** (from
  the entry criteria) wasn't quite true. A roadmap's positions can tie, so
  "move up" can silently do nothing, and nothing can take a milestone off a
  roadmap. Both needed a store method (SD-3).
- **"Add and remove from both ends"** goes beyond DESIGN-008 §5.1a, which says
  removal is always from the milestone's modal. Built as asked, and recorded as
  a deviation for Sam (choice 2).
- **"Modals (native `<dialog>` loaded by htmx)"**: only the two editors are
  loaded. The create dialogs and the member-side dialog are inline, because
  they need nothing that changes while they are open. Loading the member-side
  one too is a small change if wanted (SD-8).

## How it was verified

- **`go vet ./...` is clean, and `go test -race -count=1 ./...` passes**
  against Postgres 16 started by hand on port 54329, as the brief described.
  That includes `TestUIBrowseAndDrive` and the render tests. The new and
  changed tests are listed in the walkthrough.
- **The browser demo** ran a fresh build and `cromwell init` project on port

- **The MCP demo** ran against the same server with plain JSON-RPC calls, and
  the audit trail shows each surface's acts under its own actor.

## Follow-ups, in rough priority order

1. **Rename, re-describe and delete milestones and roadmaps.** Nothing can do
   any of them yet, and now two surfaces can create them. A delete could be
   limited to milestones that are empty and on no roadmap. This is the likely
   next small job.
2. **Checklists and jobs (M5).** The picker is a union with one branch per
   member type, so a checklist is one more branch and one more icon. The
   `milestone_members` CHECK must admit `checklist`, and `add_milestone_member`'s
   `member_type` grows.
3. **The size roll-up tree and the filterable work list** (Stage B entry
   criterion 5) aren't on the roadmap at all. They need a home.
4. **Owner pages don't refresh live** when the chat agent changes their plan.
   The tools signal the SSE hub, but entity pages only listen on the document
   page.
5. **A refused "mark as shipped" leaves no audit row.** `LockMilestone` audits
   `gate.evaluated` and then fails, so the transaction rolls it back. This
   predates M4.
6. **`POST /api/milestones/lock` reports every failure as a G4 409**, including
   "already locked". Left alone because the CLI is being retired.
7. **The milestone progress line says "1 of 1 items"**, from the existing
   `milestone-progress` partial.

## Traps for the next session

- **`TestMCPAdvertisedToolSetIsExactlyTheAuthoringSet` is shared.** M3 and M4
  both edited it; the final M4 merge combined the two lists by hand (twenty-five
  tools, with M3's relay tools). Anyone adding a tool edits the same list.
- **The member-side and editor forms post to the same routes.** Anything that
  changes how responses are chosen must keep `from=member` and the
  `HX-Boosted` check, or a boosted post will get an editor fragment as its
  whole page.
- **A project served from a long path won't start.** The unix socket path has
  a 108-byte limit; serving from a deep scratch directory fails with
  `bind: invalid argument`. The demo used `/var/tmp/m4demo`.
